# Build a trusted multi-source skill index

Skil should expand beyond its weekly skills.sh ingestion, but it should not compete on raw catalog size. The simplest useful version is a merged discovery index that stays around **20,000 skills** and classifies the **top 1,000 across all sources each week**. **skills.sh remains the main source and adoption baseline; SkillsMP adds breadth; AgenticSkills adds curated picks.** Official company skills and individual creator skills can be combined in one GUI-facing **Creators** view, while their original source and publisher remain visible in the data. AI Agents Library belongs in a workflow/topic type, not in the same installable-skill corpus, while Awesome Skills should remain blocked pending API verification and agent-skills.cc should be treated as an unverified popularity input. The current four-table skills.sh cache is a sound read model but not a multi-source index. The recommended path is additive: introduce a small merged table and source adapters, then reuse the existing weekly classification and shelf machinery without breaking existing preview or installation behavior.

## The current weekly mirror is reliable but too narrow

**Observed.** The market path is separate from Skil's local installed-skill engine. `MarketSync` crawls skills.sh listings, hydrates descriptions and hashes, classifies the top 1,000 rows, and writes role/field shelves. The database currently has `market_roles`, `market_fields`, `market_skills`, and `market_field_skills`; `market_skills.id` is the primary key, and the record is a thin listing with name, source, installs, URLs, a capped description, hash, duplicate flag, last-seen timestamp, and inactive state. Full `SKILL.md` bodies are not stored; preview fetches them live. Search uses a generated English `tsvector`, but ranks matches by installs rather than relevance. ([market schema](https://github.com/eric-huychung/skil/blob/main/supabase/migrations/0001_market_index.sql), [market store](https://github.com/eric-huychung/skil/blob/main/src/backend/supabase-market-store.ts), [market client](https://github.com/eric-huychung/skil/blob/main/src/backend/market-skills-client.ts))

**Observed.** The scheduled GitHub Action runs every Sunday at `0 0 * * 0` and invokes `--classify-only`; it does not perform the full listing crawl. Full recrawls are operator/laptop work, and a full crawl can mark missing rows inactive only after successful completion. Classifier failure preserves the previous shelves, which is a valuable fail-closed property. ([sync workflow](https://github.com/eric-huychung/skil/blob/main/.github/workflows/sync-market.yml), [sync script](https://github.com/eric-huychung/skil/blob/main/scripts/sync-market.ts), [sync orchestration](https://github.com/eric-huychung/skil/blob/main/src/backend/market-sync.ts))

**Recommendation.** Preserve this path as a compatibility read model during the experiment. Add a small merged table beside it rather than changing the existing four tables immediately. Normalize each source to a minimal `name/description/source/source_url/repository_url/score/topic` shape, merge duplicates by repository plus skill path, keep roughly 20,000 rows overall, and feed the top 1,000 pooled rows into the existing weekly classifier. The first success criterion is not more rows; it is higher successful-install and seven-day activation rates than the skills.sh-only baseline.

## Each directory contributes a different kind of evidence

The research snapshot is point-in-time, and directory counts are not comparable: a site may count paths, repositories, search records, installs, or activity. Counts should therefore be retained as source-reported observations with a unit and timestamp, never merged into a global catalog total.

([docs](https://skills.sh/docs), [CLI](https://github.com/vercel-labs/skills)) | Keep as incumbent adoption signal and install resolver. The source conclusion is therefore asymmetric: **skills.sh supplies the main catalog and adoption signal, SkillsMP improves recall, and AgenticSkills improves precision.** The other directories are enrichment or conditional inputs. This avoids treating directory marketing claims as normalized facts while keeping the implementation small.

## Use strict eligibility with permissive discovery

**Observed.** The Agent Skills format is a directory containing `SKILL.md` with YAML frontmatter and required `name` and `description`; optional scripts, references, and assets support progressive disclosure. Cloudflare's discovery RFC proposes a `.well-known/agent-skills/index.json` with URL and SHA-256 digest fields, trusted-origin allowlists, safe archive handling, and no default script execution. ([Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx), [Cloudflare discovery RFC](https://github.com/cloudflare/agent-skills-discovery-rfc))

**Recommendation.** Let the crawler index structurally useful candidates, but reserve install recommendations and trust badges for records that pass a policy gate:

| Tier | Eligibility and UX |
|---|---|
| **A: official verified** | Vendor/foundation-owned artifact or one linked from its official domain; valid license; reproducible commit/release/digest; safety checks pass. Show official badge scoped to that artifact relationship. |
| **B: maintainer verified** | Established maintainer or educator owns a real, licensed, versioned skill pack with active history and reproducible source. Show contributor badge; never imply vendor endorsement. |
| **C: community indexed** | Valid `SKILL.md`, canonical source, license, and revision, but no official or established-maintainer relationship. Searchable, not default-recommended for sensitive work. |
| **D: reference/content** | Docs, prompts, videos, workflow pages, reference MCP implementations, or unlicensed items. Link for context, but do not present as installable/trusted skills. |
| **Quarantine/reject** | Invalid frontmatter, ambiguous ownership, unsafe archive paths, secrets, malware indicators, unexplained executable behavior, hidden network/download behavior, privilege escalation, or instructions that attempt to override host safety. |

All content is untrusted data during ingestion. Parse with bounded YAML limits, reject traversal/symlinks and oversized archives, never execute scripts, and scan in a sandbox without credentials or network by default. Record declared shell, network, filesystem, credential, and external-tool capabilities. Prompt-injection scanners and OpenSSF checks are evidence, not certification: OWASP states that prompt injection has no foolproof prevention, while Scorecard checks are heuristics. ([OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection), [OpenSSF Scorecard](https://scorecard.dev/))

Trust must remain multidimensional and time-varying: availability, freshness, provenance, license, security evidence, content risk, and publisher identity should each show `unknown` when unverified. “Free,” “popular,” “official” in a directory, stars, and installs are not sufficient evidence. A SHA-256 digest proves integrity, not publisher identity; combine it with domain/repository ownership, cross-links, signed releases, or provenance attestations where present. ([SLSA provenance](https://slsa.dev/spec/v1.0/provenance), [Sigstore](https://docs.sigstore.dev/cosign/signing/other_types/), [NIST AI RMF profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence))

## Canonicalize identities, revisions, and source observations

The central data-model change is to separate a logical capability from where it was observed and which immutable content was fetched. A URL, repository, branch, or display name is not a stable identity because URLs move, repositories fork, and a repository can contain many skills.

**Recommendation.** Introduce these logical entities in a new index, initially populated alongside `market_skills`:

| Entity | Purpose and minimum fields |
|---|---|
| `skill` | Canonical capability: stable ID/slug, name, summary, status, identity confidence, canonical publisher, type, tags, compatibility, and relationship history. |
| `skill_source` | One provider observation: provider, source-native ID, canonical/original URL, repository ID/path, adapter version, ownership relationship, install spec, and source health. |
| `skill_revision` | Immutable content state: source ID, ref/commit/blob, SHA-256, raw object reference, normalized frontmatter/body hashes, parser status, release/channel, observed and source dates. |
| `publisher` | Vendor/org/person identity, verified domains/namespaces, linked repositories, claim status, and moderation history. |
| `evidence` | Typed, time-stamped claim: license, commit, signature, Scorecard, secret scan, prompt-risk scan, install smoke test, audit, report, or official cross-link. |
| `observation` | Append-only source payload hash, source metrics, rank/window, ETag/Last-Modified, fetch result, and observed time. |
| `collection` | Curated grouping with curator, rationale, audience, inclusion and review/expiry dates. |

Use a provider adapter contract such as `discover`, `getHead`, `listCandidates`, `getRevision`, `getEvidence`, and `installSpec`. A GitHub adapter should resolve repository metadata, changed paths, commits, contributors, license, releases, workflows, and security files. Direct HTTPS and `.well-known` adapters follow the same observation contract; SkillsMP and skills.sh adapters remain provider-specific. Store raw provider payloads in append-only object storage or a raw-observation table so parsers can be re-run without recrawling.

Deduplication should be deterministic before it is semantic. First match exact canonical source/repository/path; then package URL/subpath where applicable; then identical normalized bundle digest; then immutable provider identity such as repository ID plus path plus commit/blob. Fuzzy names, descriptions, embeddings, forks, and mirrors should only create merge candidates for review. Preserve `same_as`, `fork_of`, `variant_of`, and `supersedes` relationships. A new body hash is a new revision, not an overwrite; a missing source becomes stale or source-inactive before global tombstoning.

The first implementation can remain on Supabase/Postgres. Add relational provenance and immutable revision tables, `tsvector` plus `pgvector` for hybrid retrieval, GIN/HNSW indexes, and a durable job table or queue. Supabase documents lexical/vector hybrid search and Reciprocal Rank Fusion as a suitable pattern. ([Supabase hybrid search](https://supabase.com/docs/guides/ai/hybrid-search), [pgvector](https://supabase.com/docs/guides/database/extensions/pgvector)) Keep network, scanning, and LLM work in workers, not request handlers. Preserve the current `MarketStore` seam and project approved records into the existing shelf API until a new response contract is justified.

## Make discovery explainable, diverse, and outcome-driven

The current search is exact-ish full-text matching followed by install count. That is a useful baseline but insufficient for multi-source results: it cannot distinguish relevance from popularity, freshness, official status, source family, or duplicates. The replacement should retrieve lexical and semantic candidates, then rank a visible score vector rather than an opaque composite.

**Recommendation.** Rank in this order: hard eligibility filters, query relevance and compatibility, then quality, trust, maintenance/freshness, adoption, and user outcomes. Preserve each signal with provider and timestamp. Apply source-family and near-duplicate caps, diversity across publishers, time decay, and a small exploration allocation for new verified items. Use Bayesian smoothing for feedback and Wilson-style lower bounds when ratings eventually exist. Never let a single copied repository or a directory's self-reported popularity fill the page. ([Google ranking systems guide](https://developers.google.com/search/docs/appearance/ranking-systems-guide), [npm registry API](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md))

The result card should answer “what is this?” before “install”: purpose, artifact type, publisher, exact source path, revision/digest, license, supported hosts/framework versions, declared capabilities, last observed/updated dates, audit/scan evidence, and install command. Explain rank in plain language, such as “matches testing, source is verified, updated 12 days ago, and three installs succeeded.” Show uncertainty and never call an item “safe.” Search should support lanes and filters for official, contributor, curated, workflow, MCP, instruction, platform, framework version, license, freshness, and capability risk.

Collections should evolve from the current checked-in YAML picks into versioned records with curator, rationale, audience, inclusion date, and review expiry. That enables small, high-signal shelves such as “official Next.js guidance,” “maintained React review workflows,” and “safe defaults for a new repo” without pretending that a classifier or install count is editorial judgment. Keep last-known-good shelves and expose a generation timestamp; later make shelf replacement transactional because the current delete-then-insert path can leave partial shelves after a mid-write failure.

## Creators combine official and contributor sources

**Observed.** There is already a substantial first-party corpus: Anthropic's `anthropics/skills`, Vercel/Next.js skills, Supabase's `supabase/agent-skills` with releases/tests and a `.well-known` index, Cloudflare's skills, Google's ADK/skills material, Microsoft's MCP catalog, GitHub's official MCP server, and the MCP Registry. These sources are not uniform: some are native `SKILL.md`, some are MCP, instruction files, or documentation. ([Anthropic](https://github.com/anthropics/skills), [Vercel](https://github.com/vercel-labs/agent-skills), [Next.js](https://github.com/vercel/next.js/tree/canary/skills), [Supabase](https://github.com/supabase/agent-skills), [Cloudflare](https://github.com/cloudflare/skills), [Google](https://github.com/google/skills), [Microsoft MCP](https://github.com/microsoft/mcp), [GitHub MCP](https://github.com/github/github-mcp-server), [MCP Registry](https://registry.modelcontextprotocol.io/))

**Recommendation.** Put Anthropic, Vercel/Next.js, Supabase, Cloudflare, Google, Microsoft, and GitHub sources into one GUI-facing **Creators** view alongside individual creators. Keep `publisher_type` and `source` internally so the UI can show “Official” or “Creator” when useful, but do not make verification a launch blocker. Ingest MCP, `AGENTS.md`, `CLAUDE.md`, Copilot instructions, plugins, and docs as their original types; do not silently convert them into skills.

Matt Pocock and Addy Osmani should be included now as creator sources. Matt's repository contains real `SKILL.md` workflows, plugin metadata, installation instructions, and invocation distinctions. Addy's repository contains skills, agents, references, adapters, eval cases, setup guides, and an MIT license. Both can appear in the same Creators view as official company sources, while remaining clearly labeled as creator-authored rather than company-endorsed. ([Matt Pocock skills](https://github.com/mattpocock/skills), [Addy Osmani agent skills](https://github.com/addyosmani/agent-skills))

Maintain a watchlist for other educators and maintainers, but ingest only when a real, licensed, reproducible skill/plugin/instruction artifact exists. Reputation, a course, a blog, or a prompt collection is not an artifact. Contributor profiles should show authorship, license, collaborators, update history, evaluations, reports, and endorsement status separately from skill quality.

## Phase the roadmap around evidence before scale

| Phase | Scope | Exit condition |
|---|---|---|
| **0: merged-index experiment, 0-4 weeks** | Add a `market_discovery` table and minimal source adapters; keep roughly 20,000 merged rows; import skills.sh, SkillsMP, and AgenticSkills; dedupe by repository plus skill path; reuse the existing top-1,000 weekly classification; add GUI-only Top, Trending, Creators, and Topics views. | The merged table updates safely; source and URL are visible; existing skills.sh behavior remains unchanged; no source outage mass-deletes the index. |
| **1: improve the experiment, 1-3 months** | Add changed-skill detection, source metrics, topic reuse, creator/publisher metadata, and source health. Reclassify only new or changed skills while keeping the pooled top-1,000 weekly cap. | Install success and activation can be compared against the skills.sh-only baseline; duplicate rate and source freshness are measured. |
| **2: trust and ranking, 3-6 months** | Add publisher/domain claims, digest/release linkage, license/security/provenance evidence, sandboxed static checks, install smoke tests, hybrid search, explainable score vectors, feedback/report flow, version history, and update notifications. | Successful install and seven-day activation beat installs-only baseline; every featured result has dated trust evidence; report SLA and audit trail exist. |
| **3: network and teams, 6-12 months** | Add contributor/org pages, collections/subscriptions, private catalogs, allow/deny policy export, publisher analytics, and only then package-registry adapters where demand is proven. | Repeat discovery and update adoption are measurable; team policy/audit usage justifies paid packaging without pay-to-rank. |

The concrete repo sequence is: add provider-neutral types and a new merged-table seam beside `MarketSkillsClient`; add one migration rather than repurpose `market_skills.id`; implement source adapters for skills.sh, SkillsMP, and AgenticSkills; make `MarketSync` build one pooled index of about 20,000 rows and classify only its top 1,000 weekly; then adapt `MarketStore` and the GUI read path. Do not put bodies into the existing market table. Use metadata and canonical links first, cache content only where licensing permits, and keep installation source-native through the existing adapter/engine path.

## Metrics and risks determine whether expansion is working

The north-star metric should be **successful skill outcomes per active user**: an install that succeeds and is activated/read or used for a subsequent task within seven days. Track search-to-detail CTR, detail-to-install attempt, install success and failure reason, seven-day activation, 30-day retained usage, update adoption, repeat discovery sessions, and collection save/install rate. Catalog guardrails are canonical-source/version coverage, license/compatibility/capability coverage, duplicate candidates per 100 results, confirmed duplicate rate, freshness SLA, adapter fetch/parse success, stale-result exposure, smoke-test pass rate, report rate per 1,000 installs, and median report resolution. Trust metrics include evidence-backed publisher/release verification among top results, verified namespaces, contributor response time, and the percentage of ranking attributable to explainable signals.

Primary risks are prompt injection and malicious scripts, misleading official/popularity labels, license violations from mirroring, crawler/API instability, source-rate limits, semantic over-merging, stale guidance, ranking manipulation, and privacy harm from telemetry. Mitigations are quarantine-before-LLM, sandbox/no execution, capability disclosure, least privilege, source-specific rate limits and conditional requests, immutable revisions, human merge review, source-scoped badges, metadata-first rights policy, append-only evidence, and privacy-preserving outcome aggregation. Do not add public star ratings until identity or install linkage and abuse handling exist; do not sell ranking position or trust badges. The strongest later monetization is private team catalogs, policy controls, hosted audit/install testing, update alerts, and publisher analytics, not pay-to-rank.

## Conclusion

Skil does not need to become the largest directory. It needs to make multiple directories easier to use. Keep a roughly 20,000-row merged pool, classify its pooled top 1,000 weekly, use skills.sh for the main catalog and adoption signal, SkillsMP for recall, and AgenticSkills for curated precision. Show official companies and individual maintainers together in the GUI's Creators view, with source labels rather than a heavy verification system. Keep AI Agents Library as workflow content, defer Awesome Skills until its API contract is repaired or verified, and keep agent-skills.cc below the trust boundary.

The immediate product decision is architectural: move from one mutable listing row per upstream item to canonical identity plus source observations plus immutable revisions, while projecting into the current market API until outcome data proves a new UX. That investment makes every later feature, from official badges and update alerts to team allowlists, safer and cheaper than adding more scrapers to the current weekly mirror.
